# Hardening sweep: public album share links

The public share-link feature exposes unauthenticated endpoints under `/api/v1/public/share/{slug}/*`. Treat this as the highest-risk attack surface in the codebase and audit aggressively. Fix every unambiguous issue you find.

## Scope (files in focus)

- Every handler that mounts `/api/v1/albums/{uid}/share*`, `/api/v1/shares/{slug}`, and `/api/v1/public/share/{slug}/*` (find them under `internal/web/handlers/`).
- The share cookie middleware and rate-limit middleware (likely under `internal/web/middleware/`).
- `internal/database/postgres/` files for the `album_share_links` table (migration 039 and the repository methods).
- The frontend consumer page under `web/src/pages/` (whichever directory serves `/share/<slug>`). Look at it only to confirm the wire shape it expects.

Out of scope: anything not on the share-link code path.

## What to look for

1. **Info leak before verify**
   - `GET /api/v1/public/share/{slug}/` MUST return only metadata that is safe before the password is verified: `has_password`, `expires_at`, and `album.title` + `photo_count` + `cover_thumb_url` *only if the link is public*. For password-protected links, the album payload should be hidden until the share cookie is set.
   - The cover thumbnail must not be retrievable for password-protected links until verification.
   - 404 (unknown) vs 410 (expired) responses must not differ in timing in a way that leaks existence.

2. **Password verification**
   - `POST /api/v1/public/share/{slug}/verify` uses constant-time bcrypt compare.
   - Rate limit (10 attempts per IP per 5 minutes) is enforced and the bucket is correctly keyed on (IP, slug) — not just IP, not just slug.
   - 429 response includes a correct `Retry-After` header.
   - Failed verification is logged to `audit_log` as `share_link_password_failed` with IP + UA; success is NOT logged with the cleartext password.
   - Verification on an expired or revoked link returns 410, not 200 + cookie.

3. **Share cookie**
   - Cookie name `share_<slug>` is scoped correctly (path or audience).
   - `HttpOnly`, `Secure` (under HTTPS), `SameSite` set appropriately.
   - 24h expiry matches the documented behavior.
   - Verifying a different slug does NOT grant access to the original (one cookie per slug).

4. **Photo authorization on public endpoints**
   - `GET /api/v1/public/share/{slug}/photos`, `/thumb/{size}`, and `/download` MUST verify that the requested `photo_uid` actually belongs to the linked album. A bug here would let an attacker iterate any photo UID via any share link.
   - Archived photos must NOT be exposed via public endpoints.
   - Photos with `private = true` — confirm the intended behavior (likely: excluded from public listing).

5. **Slug + listing safety**
   - Slug regex `^[a-z0-9-]{3,64}$` is enforced on creation; rejection is consistent (no panics, no stack traces).
   - Slug generation from album title applies `-N` dedup correctly under concurrent creation (consider a UNIQUE constraint + retry rather than a SELECT-then-INSERT race).
   - Pagination `limit` on photos is capped at 1000 server-side — verify the cap actually fires even when the client asks for `limit=9999`.

6. **Download endpoint robustness**
   - Range header parsing rejects malformed ranges with 416 and does not crash on `bytes=-` or huge end offsets.
   - File path resolution cannot escape the originals tree via crafted album / photo UIDs.
   - `Content-Disposition` filename is sanitized (no header injection).

7. **Revocation + expiry**
   - `DELETE /api/v1/shares/{slug}` (admin/editor) immediately invalidates the share cookie path (the next request to public endpoints returns 410 or 404).
   - `expires_at == NOW()` boundary — confirm it is treated as expired (strict `>` vs `>=` decision).
   - Deleting the underlying album cascades to share rows (FK `ON DELETE CASCADE` per the migration); after deletion, public requests return 404, not 500.

8. **Mint endpoint authorization**
   - `POST /api/v1/albums/{uid}/share` requires `HasWriteAccess` — verify against the role middleware.
   - The response NEVER contains the bcrypt hash; only `has_password: bool`.

## How to work

1. Read every file in scope and map the routing table. Note any inconsistencies between routes and middleware before changing anything.
2. For each confirmed bug: focused commit (`fix(share): ...`) with a short, accurate message. Multiple small commits are preferred over one mega-commit.
3. For ambiguous or policy-level findings: add an entry to `TODO.md` under `## Share links hardening sweep — YYYY-MM-DD`.
4. Add tests for fixes that touch non-trivial logic (rate limit, authorization, slug generation).
5. Do NOT change the documented wire shape unless the doc itself describes the bug.

## Verification

- `make lint` must pass.
- `make test` must pass.
- `make check` runs the full gate before the final commit.

## Done when

- Every confirmed bug in the categories above is fixed and committed, OR documented in `TODO.md`.
- `make check` is green.
- Final report lists fixes, deferred items, and any rate-limit / cookie behavior that was deliberately left as-is and why.
