# Robustness sweep: file path safety + upload / download / edit IO

Audit every code path that constructs file paths on disk or reads/writes files. Look for path traversal, temp-file leaks, partial-write corruption, race conditions, and crashes on decoder failure. Fix every unambiguous issue.

## Scope (files in focus)

- `internal/storage/` (originals layout `YYYY/MM/<filename>`, thumbnail cache `thumb/<aa>/<bb>/<cc>/<hash>_<size>.jpg`).
- `internal/photopipe/` (upload pipeline: buffer, hash, decode, EXIF, near-dup, write original, DB rows, thumbnails).
- `internal/thumb/` (thumbnail generation registry + `GenerateSizes` / `GenerateSizesFromImage`).
- `internal/imgedit/` (non-destructive edits render pipeline).
- `internal/imgconvert/` (HEIC/RAW intermediate JPEG production).
- `internal/exif/` (XMP sidecar writes via `exiftool` subprocess).
- Photo download handler (renders edits by default, `?original=true` bypass) and share-link download handler.
- Thumbnail-serving handler.
- Trash purge + auto-purge daemon (file deletion paths).

Out of scope: the LaTeX export pipeline (the PDF render lives in `internal/latex/` and is touched by the jobs sweep instead).

## What to look for

1. **Path traversal**
   - Any filename that comes from the user (multipart upload, EXIF, XMP sidecar destination) must be sanitized before joining onto the originals tree. Verify no `..`, no absolute paths, no NUL bytes survive.
   - Thumbnail cache paths are keyed by SHA256 (safe) — confirm the size suffix is from a fixed allowlist and cannot be user-controlled.
   - The `share/{slug}/photos/{photo_uid}/download` and the authenticated `/photos/{photo_uid}/download` handlers must resolve the file path only via the DB row, never by interpolating the UID into a path.

2. **Symlink + race safety**
   - Originals directory traversal cannot be tricked into following a symlink that escapes the originals root.
   - Concurrent uploads with the same SHA256 do not both write the original (race window between dedupe check and write). If a race exists, fix it with a unique constraint + idempotent write, or document the trade-off.
   - Thumbnail cache writes are atomic (write to temp, rename into place) so a partial cache file is never served.

3. **Temp-file lifecycle**
   - Every upload that fails (validation, decode error, DB write error, embedding call error) deletes its temp file. Search for `os.CreateTemp` / `ioutil.TempFile` usage and confirm every path has a `defer os.Remove`.
   - HEIC/RAW intermediate JPEGs produced by `imgconvert` are cleaned up after the pipeline completes, even on error.
   - Multipart parsing has a sane `MaxBytes` / form-size limit so a malicious client cannot fill `/tmp`.

4. **Partial-write rollback**
   - `PUT /api/v1/photos/{uid}/edits` must not leave a DB row + stale thumbnail cache on save failure. Verify the rollback path (`internal/imgedit`, `internal/thumb.GenerateSizesFromImage`) restores cache to a consistent state.
   - On HEIC/RAW originals without `heif-convert` / `dcraw`, the documented behavior is "503 + rollback". Confirm rollback actually fires (no stale `photo_edits` row left behind).

5. **Range / download safety**
   - Range header parsing rejects malformed values with 416 (no panic on `bytes=-` or `bytes=a-b`).
   - `Content-Disposition` filename uses RFC 5987 or is otherwise sanitized so a crafted filename cannot inject CRLF into response headers.
   - The render-on-edits download path (`/photos/{uid}/download` default) does not pin the entire file into memory for huge originals.

6. **Decoder failures**
   - `heif-convert` / `dcraw` failures (non-zero exit) are mapped to clear HTTP error codes, not 500.
   - The Docker startup self-check WARNs (not crashes) for missing binaries — verify the dev path matches.
   - `exiftool` subprocess errors during XMP sidecar write are logged but do not fail the API request (documented behavior).

7. **Purge correctness**
   - `POST /api/v1/photos/batch/purge` (admin) and the hourly auto-purge daemon must delete: the photo row (cascades phashes / markers / files / album_photos / photo_labels), embeddings, faces, on-disk originals, every cached thumbnail size, and the `photo_edits` row.
   - A failure during file deletion (permission, missing file) must not leave the DB row but no file, or vice versa. Confirm the order of operations and the error-handling path.
   - The daemon must hold no DB lock across long file IO.

## How to work

1. Build a mental list of every file write / read site in scope before changing anything.
2. For each confirmed bug: focused commit (`fix(storage): sanitize ...`, `fix(upload): clean temp file ...`) with a short message and, where applicable, a regression test.
3. For ambiguous cases (e.g. race windows that need a schema change): add an entry to `TODO.md` under `## File IO hardening sweep — YYYY-MM-DD`.
4. Where a fix involves filesystem behavior, test with a small fixture file (a tiny JPEG or PNG checked into `internal/photopipe/testdata/` is fine).

## Verification

- `make lint` must pass.
- `make test` must pass.
- `make check` runs the full gate.

## Done when

- Every category above has been audited and the bugs either fixed or recorded in `TODO.md`.
- `make check` is green.
- Final report summarizes fixes, deferred items, and any decoder-failure path that needs operator attention (e.g. a missing binary).
