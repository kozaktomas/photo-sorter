# Hardening sweep: auth, sessions, user management

Audit the authentication, session handling, and user-management code paths for functional and security bugs. Fix every unambiguous issue you find in this sweep.

## Scope (files in focus)

- `internal/auth/` (password hashing, role constants, bootstrap, validators, `EnsureNotLastAdmin`).
- `internal/web/middleware/` (auth + role middleware).
- `internal/web/handlers/auth.go` (login, logout, status).
- `internal/web/handlers/users.go` (admin user management).
- `internal/web/handlers/me.go` if present (self-management endpoints).
- `internal/database/postgres/sessions.go` (session store).
- Cookie / `Secure` flag detection logic and `SameSite` settings wherever they live.
- Audit log integration for login + user mutations.

Out of scope: share-link auth (a separate task covers that).

## What to look for

Bug categories — for each, walk through the relevant code and verify behavior. Examples are non-exhaustive; report anything similar you spot.

1. **Cookie security flags**
   - `HttpOnly` set on every auth-related cookie.
   - `Secure` correctly auto-detected behind a reverse proxy (`X-Forwarded-Proto`, direct TLS) and not set on bare HTTP localhost development.
   - `SameSite=Strict` (or `Lax` if cross-origin is genuinely needed) — verify the intent matches the value.
   - Path / Domain attributes scoped correctly.

2. **Session lifecycle**
   - Session ID rotated on login (no session fixation).
   - Session deleted from the DB on logout (not just the cookie cleared client-side).
   - Sessions tied to `user_uid`; expired or revoked sessions cannot be reused.
   - Sliding expiry vs absolute expiry — confirm which is implemented and that it matches expectations.
   - Server restart: persisted sessions survive (cookie+DB) without privilege escalation.

3. **Login / password handling**
   - Password comparison uses constant-time bcrypt compare (no early-exit timing leak).
   - No information leak between "user does not exist" and "wrong password" (both paths take similar time and return identical error messages).
   - Disabled users cannot log in.
   - Failed login attempts are written to `audit_log` (`login_failed`) with IP + UA, but the response does NOT echo the attempted username back to the audit log in a way that allows log-injection.
   - Some form of brute-force friction exists (rate limit / lockout) — if missing, flag it in `TODO.md` rather than guessing the right policy.

4. **User-management endpoints (`/api/v1/users/*`)**
   - All mutating endpoints require admin role; double-check the middleware actually fires (no route accidentally outside the protected group).
   - `EnsureNotLastAdmin` is called on every code path that could leave zero admins: delete user, disable user, change role admin → editor/viewer.
   - Password reset endpoint cannot be used by non-admins to reset arbitrary users.
   - Username + password validators (`ValidUsername`, `MinPasswordLength`) actually run on every relevant endpoint, not just the create path.
   - Audit log row written for every mutation (create / update / password / disable / delete) with the acting admin's `user_uid`.

5. **Self-management endpoints (`/api/v1/me/*`)**
   - `POST /me/password` requires the current password and rejects when it does not match.
   - Cannot change own role, UID, username via this endpoint (only password / display fields if any).
   - Audit log row written.

6. **Bootstrap admin**
   - If both env vars are unset and the `users` table is empty, the server logs a clear WARN and starts (does not crash).
   - Bootstrap is idempotent — re-running with the vars set after a user exists must NOT create a duplicate or alter the existing admin password.

## How to work

1. Read every file in scope. Spend a few minutes mapping the call graph before changing anything.
2. For each bug you confirm: write a focused commit (`fix(auth): ...`) with a short, accurate message. Multiple commits are fine — keep each diff small.
3. For each ambiguous finding (policy question, risky refactor, missing-feature flag): add an entry to `TODO.md` under a new `## Auth / session hardening sweep — YYYY-MM-DD` heading. Do not implement.
4. Add or extend tests where the fix is non-trivial (`internal/auth/*_test.go`, handler tests). Do not chase 100 % coverage — focus on the bug you just fixed.
5. Update `docs/API.md` or `CLAUDE.md` only if a documented behavior was wrong (rare; in most cases the doc task will sweep those later).

## Verification

- `make lint` must pass.
- `make test` must pass.
- `make check` is the full gate — run it before the final commit.
- Pre-commit hook will re-run lint; do not bypass it.

## Done when

- Every confirmed bug in the categories above has been fixed and committed, OR added to `TODO.md` with a one-line rationale why it was deferred.
- `make check` is green.
- A short summary at the end of the task report lists what was fixed, what was deferred, and where the deferred items live in `TODO.md`.
