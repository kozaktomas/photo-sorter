# Preserve PhotoPrism photo_uid Across Migration

**This is a correctness blocker for the entire PhotoPrism → native migration.** Without it, any data already in the photo-sorter native Postgres database (books, embeddings, faces, markers, etc.) becomes orphaned the moment `migrate-from-photoprism` runs, because the migrator assigns brand-new native UIDs to imported photos instead of preserving the PhotoPrism UIDs the rest of the schema has been referencing since day one.

## Background

photo-sorter has been deployed for months with PhotoPrism as the source of truth for photos and a native Postgres database for everything else. The following native tables all carry a `photo_uid VARCHAR(32)` column that today holds PhotoPrism's UIDs (the migration that created `embeddings` literally says so: `-- photo_uid references PhotoPrism`):

- `embeddings` (768-dim CLIP, populated by the embedding pipeline against PhotoPrism's photo list)
- `faces` (512-dim InsightFace, plus cached PhotoPrism marker geometry)
- `faces_processed` (tracking)
- `markers` (PhotoPrism-style face markers cached locally)
- `album_photos` (native album membership; rows added today key on PhotoPrism photo_uids)
- `photo_labels` (native label assignment)
- `photo_phashes` (perceptual hashes; this one has an FK to `photos(uid)` ON DELETE CASCADE)
- `section_photos` (book pre-pick pool; the comment in migration 008 says "photo_uid references PhotoPrism")
- `page_slots` (book layout slots)

When `migrate-from-photoprism` runs today, it inserts new rows into `photos` with freshly generated UIDs — see `internal/migrate/stage_photos.go:337-340` (`buildPhotoRecord`): the returned `*database.Photo` does NOT set `UID`, so `CreatePhoto` assigns a new one. The migrator keeps the mapping in memory (`m.photoMap[ppPhotoUID] = nativeUID`) and uses it only inside the same run (for stages like `markers` and `albums` that need to look up the new UID from the old). The mapping is discarded at the end. **Every reference in every other table — including months of user-created book layouts and embeddings — is left dangling.**

## Goal

After this task:
1. `migrate-from-photoprism` writes new `photos` rows whose `uid` column equals the source PhotoPrism `photo_uid` verbatim.
2. All existing native-DB rows that reference PhotoPrism UIDs (embeddings, faces, books, etc.) reconnect to their photo with zero remap work.
3. Idempotent re-run continues to work: skipping by file_hash still wins, and a second run that encounters an already-migrated photo with a matching UID is a no-op.
4. The migrator emits the photo-UID map as a JSON file so an operator who has already run the broken version can run a separate "remap" pass on their data.

## Requirements

### 1. Preserve UID in `buildPhotoRecord`
- In `internal/migrate/stage_photos.go`, change `buildPhotoRecord` so the returned `*database.Photo` sets `UID: p.PhotoUID`.
- PhotoPrism UIDs are 16-character base32 strings; the native `photos.uid` column is `VARCHAR(32) PRIMARY KEY` and accepts them without modification.
- Search for any other migrator stage that creates rows with UIDs derived from PhotoPrism entities (albums via `album_uid`, labels via `label_uid` or slug, subjects, markers via `marker_uid`) and verify they all preserve the PhotoPrism UID as well. If `stage_albums.go` / `stage_labels.go` / `stage_subjects.go` / `stage_markers.go` currently generate new UIDs, change them to preserve the PhotoPrism UIDs for the same reason. Each of those entities is also referenced by `photo_uid`-style soft FKs from other tables.

### 2. Handle the "native row already has that UID" case
- `CreatePhoto` will return a UNIQUE-violation on `uid` if a row already exists. Today `handleCreateConflict` only handles UNIQUE-on-`file_hash`. Extend it to:
  - On `uid` collision with matching `file_hash`: treat as "already migrated", record the mapping using the existing native row, increment `Skipped` (already the behavior).
  - On `uid` collision with DIFFERENT `file_hash`: this is the legacy-data-from-a-broken-migration case. Log a clear error message:
    ```
    photo <uid>: UID collision with an existing native row carrying a different file_hash. This usually means a previous (buggy) migration created native rows with generated UIDs. Run `photo-sorter migrate-remap-references` after this command finishes (see --emit-photo-map).
    ```
    Skip this photo (count as `Failed`), continue with the rest.

### 3. Emit the photo UID map
- Add a flag `--emit-photo-map <path>` to `migrate-from-photoprism`. When set, after the photos stage finishes, write a JSON file of the form:
  ```json
  {
    "version": 1,
    "generated_at": "2026-05-21T14:30:00Z",
    "source": "photoprism",
    "photo_uid_map": {
      "pq1234...": "pq1234..."
    },
    "file_uid_map": {
      "fu0987...": "pq1234..."
    }
  }
  ```
  In the happy path (this task lands first and is the only migration), `photo_uid_map` is identity (`source == destination`). It still has value: a downstream `migrate-remap-references` (next sub-task below) can verify there is nothing to remap, and an operator can inspect the file.
- Default path when the flag is omitted: do not emit. (Keeps the dry-run / quick-test flow clean.)

### 4. Add `migrate-remap-references` CLI
- New Cobra command `migrate-remap-references` in `cmd/migrate_remap_references.go`.
- Flags:
  - `--map <path>` (required): JSON written by `migrate-from-photoprism --emit-photo-map`, OR a hand-written file by the operator.
  - `--dry-run` (bool, default false): print row counts that would change, do not write.
  - `--yes` (bool, default false): skip the interactive confirmation prompt.
- Behavior: for each `(old_uid, new_uid)` pair in the photo map where `old_uid != new_uid`, run UPDATE statements against:
  - `embeddings SET photo_uid = new WHERE photo_uid = old`
  - `faces SET photo_uid = new WHERE photo_uid = old`
  - `faces_processed SET photo_uid = new WHERE photo_uid = old`
  - `markers SET photo_uid = new WHERE photo_uid = old`
  - `album_photos SET photo_uid = new WHERE photo_uid = old`
  - `photo_labels SET photo_uid = new WHERE photo_uid = old`
  - `section_photos SET photo_uid = new WHERE photo_uid = old`
  - `page_slots SET photo_uid = new WHERE photo_uid = old`
  - `photo_phashes`: this one has a CASCADE FK, so updating `photos.uid` directly is not safe with active phashes; phash rows must be remapped first OR the FK temporarily relaxed. Simplest: in a single transaction, `UPDATE photo_phashes` first, then `UPDATE photos`. The CASCADE on the FK only fires on DELETE, not UPDATE, so this is safe as long as the order is right and both happen in one transaction.
  - Also update `file_uid_map` references in `markers.file_uid` and `photo_files.file_uid` (if such a table exists; verify by `\d photo_files` against the dev DB).
- Wrap the whole thing in a single Postgres transaction. Either everything remaps or nothing does.
- After applying, run an integrity audit: count rows in each soft-FK table whose `photo_uid` no longer matches any `photos.uid`. Print the orphan counts in the summary. Non-zero is a warning, not an error (some orphans may exist for unrelated reasons, e.g. deleted PhotoPrism originals).
- For a happy-path map where `old == new` for every key, the command must detect this and exit immediately with a "nothing to remap" message.

### 5. Documentation
- `CLAUDE.md` migration roadmap section: add a sentence under the migration paragraph stating "`photo_uid` from PhotoPrism is preserved as the native photo UID; downstream tables (`embeddings`, `faces`, `section_photos`, `page_slots`, ...) keep their references without remap."
- `docs/cli-reference.md`: document `migrate-from-photoprism --emit-photo-map` and the new `migrate-remap-references` command.
- Add a section to `docs/specs/` (or wherever migration runbooks live) titled "Cross-server migration with existing photo-sorter data" describing the recommended workflow:
  1. On the old host: `photo-sorter db-export -o sorter.sql.gz`.
  2. On the new host: install fresh photo-sorter, `db-import` the dump.
  3. rsync originals from the old PhotoPrism host to `STORAGE_ORIGINALS_PATH`.
  4. Open MariaDB to the new host (or SSH tunnel).
  5. Run `migrate-from-photoprism --emit-photo-map /tmp/photo-map.json ...`.
  6. (If the operator has legacy data from a pre-fix migration) `migrate-remap-references --map /tmp/photo-map.json`.

  - `photos.uid` equals the PhotoPrism `photo_uid` for every migrated row.
  - A test fixture row in `embeddings` keyed on the PhotoPrism UID is still findable by `SELECT ... FROM photos JOIN embeddings ON photos.uid = embeddings.photo_uid` after migration.

## Edge Cases

- **PhotoPrism UID format**: 16 chars, lowercase, prefix `p` for photos / `s` for subjects / `a` for albums / `l` for labels / `m` for markers. Don't validate the format inside the migrator — the source DB is the authority. If PhotoPrism ever emits a UID that does not fit `VARCHAR(32)`, the INSERT will fail with a clear error; that's good enough.
- **Subjects, albums, labels, markers**: PhotoPrism UIDs for these entities also currently flow into the native `subjects.uid`, `albums.uid`, `labels.uid`, `markers.uid` columns via the existing migrator. Audit whether the current code preserves THEIR PhotoPrism UIDs (it probably does — the bug seems specific to `photos`). Document the audit result in the commit message and fix any other entity that has the same issue.
- **Native uploads after migration**: photos uploaded directly through the native upload pipeline (not via PhotoPrism) get UIDs from photo-sorter's own generator. Format will differ from PhotoPrism's — both formats must coexist in `photos.uid`. That's fine; the column is `VARCHAR(32)`.
- **Migrator already used in the operator's environment**: per the user's note in the task that motivated this, the operator has NOT yet run the production migration. So no remap-references run is needed for the happy path. The command is added for robustness and for any future operator who lands the buggy version first.
- **Concurrent re-run**: the existing UNIQUE-on-`file_hash` protection still wins for "same photo, already migrated" cases. The new UNIQUE-on-`uid` protection covers "different photo, same UID" — never expected, but worth catching.

Verify with `SELECT count(*) FROM section_photos sp JOIN photos p ON sp.photo_uid = p.uid` that the join count matches the input row count — i.e., zero orphans.

The book editor must render the cover photo, the section photo pool, and every page slot exactly as before.
