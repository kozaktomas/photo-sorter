# Docker Runtime Decoders: dcraw + heif-convert + exiftool

The current Dockerfile installs only TeX, `postgresql-client`, and CA certs in the runtime stage. The Go upload pipeline shells out to three external tools that the image does NOT contain, so the following features silently fail at runtime in any container deployment:

- **RAW upload** (NEF / CR2 / CR3 / ARW / DNG / RAF / ORF / RW2 / PEF / SRW) — `internal/imgconvert/raw.go` calls `exec.LookPath("dcraw")`; the lookup fails and the upload returns `ErrConverterMissing`.
- **HEIC / HEIF upload** — `internal/imgconvert/` shells out to `heif-convert` (provided by Alpine's `libheif-tools` package).
- **EXIF edit endpoint** (`PUT /api/v1/photos/{uid}/exif`) — writes the XMP sidecar via an `exiftool` subprocess. Without exiftool, the DB row is updated but the on-disk XMP sidecar is silently skipped (the handler logs and continues).

This task adds all three tools to the runtime image and adds a startup self-check so the next image regression is loud, not silent.

## Requirements

### 1. Install the three decoders in the runtime stage of `Dockerfile`
- Extend the existing `apk add --no-cache` line in the final `FROM alpine:3` stage to also install:
  - `dcraw` (Alpine community repo; provides the `dcraw` binary the Go code calls with `-c -w -h`)
  - `libheif-tools` (provides `heif-convert`)
  - `exiftool` (Alpine package name is `exiftool`; provides `/usr/bin/exiftool`)
- If `dcraw` or `libheif-tools` are not in `main` repo, enable `community` repo for the install line. The right pattern in Alpine 3.x:
  ```
  apk add --no-cache --repository=https://dl-cdn.alpinelinux.org/alpine/v3.21/community \
      dcraw libheif-tools
  apk add --no-cache exiftool
  ```
  Verify the Alpine version pinned by the `FROM alpine:3` tag at build time and use the matching `v3.X` URL — or, simpler, just rely on `community` being enabled by default in recent `alpine:3` tags (since 3.17) and drop the explicit repo URL. The implementing agent should check `docker run --rm alpine:3 apk policy dcraw` to confirm before deciding.
- Keep the existing TeX / postgresql-client / fontconfig / curl install logic. Order matters for the `apk del curl unzip` cleanup at the end — add the new packages BEFORE that cleanup so curl is still around if you need it for one of them; the new ones do not need curl, so order does not actually matter, but keep the diff small.
- The image size will grow by ~50 MB (texlive dominates; dcraw is tiny, libheif-tools ~5 MB, exiftool ~30 MB). Acceptable.

### 2. Startup self-check in `cmd/serve.go`
Add a function that runs once during server startup (after config load, before HTTP listen) which:
- Calls `exec.LookPath` for `dcraw`, `heif-convert`, and `exiftool`.
- For each missing binary, logs a `WARN` line of the form:
  ```
  startup: dcraw not found in PATH — RAW uploads (NEF/CR2/CR3/ARW/DNG/...) will fail
  startup: heif-convert not found in PATH — HEIC/HEIF uploads will fail
  startup: exiftool not found in PATH — EXIF edits will not write XMP sidecars
  ```
- Does NOT exit. The server should still start (these are non-fatal for the deployment scenarios that don't need them, e.g. someone uploading only JPEGs). A warning in the log is enough.
- Add a one-line summary at the end: `startup: external decoders OK` when all three are present.

Put the self-check function in a new file `cmd/decoders_check.go` (small, focused) and call it from `runServe`.

### 3. Tests
- Add a unit test for the self-check function: stub `exec.LookPath` (or use a small interface for path lookup) and verify both the "all present" and "one missing" code paths log the expected line and do not return an error.
- Smoke test the converter wrappers: `internal/imgconvert/raw_test.go` and the HEIC counterpart already exist (or should). Confirm they remain green; if they were skipping when the binary is missing on the test host, leave that skip behaviour in place — CI will still cover them when run on a host that has the binaries.

### 4. Documentation
- `CLAUDE.md`: under "Supported formats" near the migration roadmap section, change the line that currently reads "RAW (CR2/NEF/ARW/DNG/... via `dcraw`)" to also call out the requirement: "RAW (CR2/CR3/NEF/ARW/DNG/RAF/ORF/RW2/PEF/SRW) via `dcraw`, HEIC/HEIF via `heif-convert`, EXIF sidecars via `exiftool`. All three are bundled into the official Docker image and listed as `Depends:` in the .deb."
- `docs/architecture.md` (or wherever the storage/upload pipeline is described): one sentence noting the external-decoder dependency and that the server emits a startup warning when any are missing.
- `README.md`: if it lists supported formats, sync that list with the imgconvert extension map. Add a one-line note for self-builders: "dcraw, libheif-tools, exiftool must be on PATH for full upload support."

### 5. Sanity check the existing extension map
While here, audit `internal/imgconvert/imgconvert.go`'s `extFormats` map. The current entries cover the major vendors (CR2/CR3/NEF/ARW/DNG/RAF/ORF/RW2/PEF/SRW). Confirm dcraw on the target Alpine version actually decodes each of these. If any vendor has been dropped or renamed in newer dcraw, log that in the task's commit message — do not silently change the map.

## Edge Cases
- The Alpine `dcraw` package version may lag behind. Newer Nikon Z-series files (e.g. NEF from Z9) sometimes need a recent dcraw or `LibRaw`. If the operator's test files do not decode, the fallback is to swap dcraw for the `darktable` CLI or `dcraw_emu` from LibRaw — but that is a larger change. For this task, just install Alpine's `dcraw` and document the limitation in the commit message: "Alpine dcraw is the standard build; very recent Nikon bodies may need a LibRaw-based decoder, tracked separately."
- The startup self-check must work in unit tests on hosts that DO have the binaries (it should pass) and on hosts that DON'T (it should log the warning). Tests should not require the binaries.
- Image size: TeX already dominates the image. Adding ~35 MB of extra tools is fine. Do not split into a separate "decoders" stage.

## Verification
- `make build` succeeds.
- `make check` passes.
- `docker build -t photo-sorter:test .` succeeds.
- `docker run --rm photo-sorter:test sh -c "command -v dcraw && command -v heif-convert && command -v exiftool"` prints three paths.
- `docker run --rm photo-sorter:test ./photo-sorter serve` (with a fake / missing DATABASE_URL — it should fail at DB connect, not at decoder check) emits the `startup: external decoders OK` log line before the DB error.
- Upload a sample NEF, CR2, and HEIC file through the running container's `/api/v1/upload` and confirm the upload succeeds and a thumbnail is generated. Use a known-good RAW from the operator's library; if none is handy, grab a public sample (e.g. https://raw.pixls.us/ has free-license samples).
- `PUT /api/v1/photos/{uid}/exif` with a `description` change writes both the DB row and the XMP sidecar (verify with `exiftool -Description <file>.xmp`).
