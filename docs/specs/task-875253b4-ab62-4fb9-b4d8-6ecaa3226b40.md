# Duplicate detection at upload

Surface a near-duplicate warning in the upload flow so the user can decide whether to keep the new file. Exact-hash duplicates are already caught by the upload pipeline (returns `ErrDuplicate`). This task adds the perceptual-hash + embedding check for near-duplicates.

## Requirements

### Backend

- Extend `internal/photopipe.Pipeline.Ingest` with a `CheckNearDuplicates bool` option (default true for web upload, false for migration).
- After step 4 (exact-hash check) and before write, compute pHash (`internal/fingerprint`) for the decodable image. Query `database.PhotoReader` for photos whose pHash differs by ≤ 8 bits AND/OR whose CLIP embedding cosine distance is < 0.05 (use the existing HNSW embedding index).
- Add a new field to the result: `NearDuplicates []DuplicateMatch` where `DuplicateMatch` contains `photo_uid`, `file_name`, `taken_at`, `score_phash int`, `score_embedding float64` (0–1, where 1 is identical).

To avoid storing pHash forever, persist it in the existing `embeddings` table as a small extra column OR add a new `photo_phashes (photo_uid PK, phash BIGINT, dhash BIGINT)` table — pick the new table approach (cleaner, doesn't bloat the embeddings row). Add migration `034_create_photo_phashes.sql`.

Populate `photo_phashes` during upload AFTER a successful insert.

### Upload job flow

- `internal/web/handlers/upload_job.go` already streams SSE events for upload progress. Add a new SSE event type `near_duplicates` carrying the matches found for a given file.
- The frontend `DropZone.tsx` should surface these (UI hookup is part of the frontend task — for this task, just emit the event and add a backend test verifying it appears in the SSE stream).

### Configuration

- `DUPLICATE_PHASH_MAX_DIFF` (default 8)
- `DUPLICATE_EMBEDDING_MAX_DIST` (default 0.05)
- `DUPLICATE_CHECK_ENABLED` (default true)

### Tests

- Upload two visually identical JPEGs (different file hashes, e.g. one re-saved with slightly different JPEG quality) → second upload reports a near-duplicate match against the first.
- Disable the check via config → no match reported.
- pHash distance for unrelated photos is well above the threshold.

### Migration / pre-existing photos

Add a CLI command `photo-sorter cache compute-phashes [--limit N] [--concurrency N]` that walks the `photos` table and populates `photo_phashes` for any row that lacks one. Idempotent.

## Verification

- `make test` passes.
- `make lint`, `make build-go` pass.
- Manual: upload a slightly re-encoded version of an existing photo and observe the `near_duplicates` SSE event.
