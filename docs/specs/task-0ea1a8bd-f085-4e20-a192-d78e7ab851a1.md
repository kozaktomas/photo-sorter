# Consistency sweep: DB transactions, FK behavior, audit log ordering

Audit every multi-step database mutation for transactional correctness. Find missing transactions, partial-state failures, audit-log writes that happen outside the mutation transaction, and FK behavior that does not match documented expectations. Fix what is unambiguous.

## Scope (files in focus)

- `internal/database/postgres/books.go` (book hierarchy mutations: cross-section page moves, slot mutual exclusion, captions / contents slot routing).
- `internal/database/postgres/embeddings.go`, `faces.go`, `era_embeddings.go` (writer paths).
- The repository methods backing photo edits (`internal/database/postgres/` — find by grepping for `photo_edits`).
- Trash store + purge implementation (`internal/trash/`) and the auto-purge daemon.
- Audit log writer (`internal/audit/`).
- Smart album repository (filters blob + photo_count recompute).
- Share-link repository (mint with slug dedup retry).
- Migrations under `internal/database/postgres/migrations/` — read the FK definitions to confirm ON DELETE behavior.

Out of scope: anything specifically auth-related (covered by the auth sweep) and SSE / job manager state (covered by the jobs sweep).

## What to look for

1. **Multi-step mutations without a transaction**
   - Any handler that issues two or more writes (insert A, then update B; or write row + write file) must either run in a single `tx`, or document why partial state is acceptable.
   - Book editor flows are especially risky: cross-section page moves (`BookWriter.MovePageToSection` per CLAUDE.md), slot assignment with photo / text / captions / contents mutual exclusion, page reorder.
   - Photo edits: the `photo_edits` row insert and the synchronous thumbnail rebuild must either both succeed or both roll back. Today the docs say save failure rolls back — verify this is actually transactional (or the thumb regen is idempotent and safe to retry).

2. **Audit log write ordering**
   - The audit row should be written INSIDE the same transaction as the mutation, so a failed mutation does not leave a phantom audit entry, and a successful mutation always has its row.
   - If the documented "best-effort, WARN-log on failure" pattern means the audit row is written AFTER commit, confirm there is no race where the response is sent before the audit row is durable (acceptable trade-off, but worth noting).
   - Batch operations write a single row with `metadata.count` — verify this is implemented and not "one row per item".

3. **FK ON DELETE behavior matches docs**
   - `album_share_links` FK → `albums(uid)` is `ON DELETE CASCADE`. Verify the migration.
   - `smart_albums.created_by_user_uid` FK → `users(uid)` is non-cascading (saved searches survive author deletion). Verify the migration.
   - `audit_log.user_uid` FK → `users(uid)` is `ON DELETE SET NULL`. Verify and confirm the list endpoint returns an empty `user_username` (not 500) for anonymized rows.
   - `photo_edits.photo_uid` FK is `ON DELETE CASCADE`. Verify.
   - On purge: the documented cascade chain (phashes / markers / files / album_photos / photo_labels) actually fires. A SQL-level audit catches missed cascades.

4. **Slot mutual exclusion**
   - The CHECK constraint on `page_slots` (photo / text / is_captions_slot / is_contents_slot are mutually exclusive) is in the migration. Verify the writer paths set only one at a time and return a clear error on violation (not a raw SQL error to the client).
   - The partial unique index that enforces "at most one captions slot per page" — confirm it exists and a duplicate assign returns `database.ErrCaptionsSlotExists` (or the contents-slot equivalent), mapped to a clear API error.

5. **Smart-album filter validation**
   - The `filters` JSONB blob must reject unknown keys (per CLAUDE.md) — verify the parser actually enforces this with 400, not silent ignore.
   - Filters that reference deleted entities (subject, label, album) must silently drop at query time, not 500.
   - The per-call recompute of `photo_count` must not be cached stale across mutations.

6. **N+1 queries**
   - Walk the list endpoints (`/photos`, `/albums`, `/labels`, `/books/{id}`) and confirm they do not issue a per-row query for thumbnails, counts, or relations. If an N+1 exists in a hot path, fix it.

7. **Migration safety**
   - The auto-apply migrations on startup (`internal/database/postgres/migrations.go`) must be idempotent and ordered. Skim the newest 3-5 migrations for non-idempotent statements (`CREATE TYPE` without `IF NOT EXISTS`, etc.).
   - A clean install (empty DB) must apply every migration in order without error.

## How to work

1. Build a list of every multi-step write in scope before changing anything.
2. For each confirmed bug: focused commit (`fix(db): wrap ... in transaction`, `fix(audit): write inside tx`) with a short, accurate message.
3. For ambiguous cases (e.g. a multi-step write where transaction wrapping would require a repository refactor): add to `TODO.md` under `## DB consistency sweep — YYYY-MM-DD` with a one-line rationale.
4. Add tests where the fix is non-trivial (a regression test that proves the rollback path works).
5. If a migration is non-idempotent, prefer a fix-forward migration (a new migration that corrects state) over editing the existing one — never edit a migration that has already shipped.

## Verification

- `make lint` must pass.
- `make test` must pass.
- `make check` runs the full gate.
- A clean DB run: spin up the dev Postgres, drop the photo-sorter database, and confirm the binary boots cleanly with all migrations applied.

## Done when

- Every multi-step write in scope has been audited.
- Fixes committed, ambiguous items in `TODO.md`.
- Final report lists: write paths audited, transactions added, FK behaviors verified, and any architectural notes worth raising.
- `make check` is green AND the clean-DB boot works.
