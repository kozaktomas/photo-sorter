# Field-Level migrate-verify Diff

The current `migrate-verify` tool (in `internal/verify/`) only compares row counts and structural identity (existence, geometry). The audit that motivated this task showed that ~12 metadata categories were silently dropped during migration and the verify tool reported zero diffs anyway. This task widens the verifier so future migrations cannot silently lose data: every column known to be migrated is compared cell-by-cell between PhotoPrism and the native DB, and any mismatch is reported.

Run this task AFTER the two gap-fix tasks land. The verifier compares whatever the migrator is supposed to copy — so its scope grows with the migrator.

## Requirements

### 1. Per-entity field comparison

For each of the five entities the migrator handles, add a "fields" check phase that runs after the existing "structural" phase:

**Photos** — for every photo present in both sides (matched by `file_hash`), compare:
- `taken_at` (instant; tolerate ≤ 1s drift)
- `taken_at_source` (the migrator maps PhotoPrism `taken_src` → `exif|unknown`; verifier should accept either side's mapping)
- `time_zone`
- `taken_at_offset` (seconds)
- `description` (PhotoPrism `photo_caption` mapped to native `description`)
- `notes` (PhotoPrism `details.notes` → native `notes`)
- `keywords` (sorted, normalized; PhotoPrism's `details.keywords` comma-string vs native TEXT[])
- GPS: `lat`, `lng`, `altitude` (tolerate ≤ 1e-6 drift on lat/lng, ≤ 1m on altitude)
- Camera/lens: `camera_make`, `camera_model`, `lens_model`
- Exposure: `iso`, `f_number`, `exposure`, `focal_length`
- Dimensions: `width`, `height`, `orientation`
- Flags: `favorite`, `private`, `panorama`, `scan`, `quality`
- EXIF: `exif_artist`, `exif_copyright`, `exif_license`, `exif_software`

**Subjects** — matched by normalized name:
- `bio`, `about`, `alias`
- `favorite`, `private`
- `type` (person / pet / object)

**Labels** — matched by slug:
- `description`
- `categories` (sorted)
- `priority`
- `favorite`

**Albums** — matched by slug:
- `description`
- `location`, `category`, `notes`, `filter`, `album_order`
- `favorite`, `private`
- `type`

**Markers** — matched by `(file_hash, x, y, w, h)` tuple (existing geometry diff):
- `score` (tolerate ≤ 0.01 drift)
- `invalid`, `reviewed`
- Subject linkage: `subject_uid` resolves to the same person on both sides

**Album / label / photo memberships** (junction tables) — already partially covered by structural counts; widen to per-pair diff so a missing pair is reported with the photo file_hash + album/label slug, not just "1 fewer pair".

### 2. CLI behaviour
- Existing flags (`--json`, `--no-color`, `--pp-db`, `--pp-originals`) keep their semantics.
- Add `--fields-only` to skip the structural check and only run the new field-level diff (useful when iterating on migrator fixes).
- Add `--strict` flag: when set, treat tolerance-band differences (1s on dates, 1e-6 on coords) as failures. Default off.
- Exit code stays 0 on perfect match, 1 on any diff. The JSON report grows new keys per entity: `field_diffs: [ { entity, key, field, source, destination } ]`. Cap the JSON output at 1000 mismatches per field type to keep the report sane on large libraries; print a "...and N more truncated" footer in the human-readable output.

### 3. Human-readable output
- For each entity section, print a header line of the form `Photos: 12 missing | 3 field diffs (keywords: 2, panorama: 1)`.
- Then for the first 50 field diffs in that entity, print `  - <file_hash[:8]>: keywords  PhotoPrism=[a, b, c]  native=[a, b]`. Use color (red for source-has / dest-missing, yellow for dest-has-extra / source-missing) unless `--no-color`.
- Keep existing structural output above the new field section so the operator gets a single "is this clean?" view.

### 4. Performance
- Batch source DB reads in chunks of 500 photos (parameterized JOIN with IN clause). Avoid N+1 queries for keywords / details.
- Run field diff queries concurrently per entity (one goroutine per entity, errgroup). Cap total DB connections to 4 to avoid hammering either source.
- On a 50k-photo library, the full verify run should finish in under 5 minutes on the Pi.

### 5. Documentation
- Update `docs/cli-reference.md` (the `migrate-verify` entry) with the new flags and the new diff categories.
- Add a one-paragraph note in `CLAUDE.md` (under the migration roadmap section) clarifying that `migrate-verify` now provides field-level coverage and is the authoritative pre-Docker-drop gate: zero diffs from `migrate-verify` is the precondition for cancelling the PhotoPrism + MariaDB compose services.

## Edge Cases
- A photo present in PhotoPrism but not in native (or vice versa) should appear in the structural diff once, NOT also in every field-diff section. Skip field comparison when the row is structurally missing.
- Unicode normalization: `keywords` containing accented characters may be stored differently in MariaDB vs Postgres. Normalize to NFC on both sides before comparison.
- Boolean-vs-int mismatches: PhotoPrism stores booleans as `TINYINT(1)`. Compare against Go bool semantics (`0 → false`, anything else → true).
- Whitespace-only strings: trim before comparison; treat `"  "` and `""` as equal.
- Empty arrays vs NULL keywords: in PhotoPrism `details.keywords` may be empty string `""`; in native, `'{}'` TEXT[]. Treat both as equivalent "no keywords".
- Timezone-naive instants: PhotoPrism stores `taken_at` as a `DATETIME` (no TZ). Native stores `TIMESTAMP WITH TIME ZONE`. Convert PhotoPrism's value to UTC using the migrator's same algorithm before comparison.

## Verification
- `make build` and `make check` pass.
- Run against the dev DB after a fresh migration: zero diffs expected.
- Intentionally `UPDATE photos SET notes = 'oops' WHERE photo_uid = ?` on one row in the native DB, re-run verify: exactly one field diff on `notes` reported, with both values printed and exit code 1.
- Run with `--json | jq` and confirm the structure matches the description above.
- Run with `--fields-only` against the dev DB: structural diff section is skipped; field diff section runs.
- Run with `--strict`: a deliberate 0.5-second drift on `taken_at` in one row is reported (it would be tolerated without `--strict`).
- Wall time on the operator's library (run on the Pi or on Box) is under 5 minutes.
