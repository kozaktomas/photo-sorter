# Replace File-Backed HNSW with pgvector-Native HNSW

photo-sorter currently maintains two in-memory HNSW indexes — one for face embeddings (512-dim, int64 keys) and one for image embeddings (768-dim, string keys) — that are loaded at startup and optionally persisted to disk via `HNSW_INDEX_PATH` / `HNSW_EMBEDDING_INDEX_PATH`. This duplicates functionality that pgvector already provides via its `hnsw` index access method and `vector_cosine_ops` operator class. The duplication forces backup tooling to special-case `.hnsw` files, makes graceful shutdown slow (`stop_grace_period: 60s` exists for index serialization), and means a `pg_dump` is not a complete metadata snapshot.

The goal of this task is to collapse all vector similarity search onto pgvector so that:
- A `pg_dump` of the `photosorter` DB is a complete metadata backup. No external index files exist.
- The Go process holds zero in-memory vector data structures. Memory footprint drops to the pool overhead.
- There are no environment variables for HNSW file paths and no manual "Rebuild Index" button — pgvector maintains the index on INSERT/UPDATE/DELETE automatically.

The public REST API behaviour must remain identical: same request shapes, same response shapes, same ranking semantics (cosine distance). Ranking results should be substantively equivalent to the in-memory implementation; minor reorderings near tie thresholds are acceptable.

## Requirements

### 1. Database migration
- Add a new migration `internal/database/postgres/migrations/035_pgvector_hnsw_indexes.sql` (renumber if 035 is already taken — use the next free three-digit prefix).
- Create an HNSW index on `embeddings.embedding` using `vector_cosine_ops`.
- Create an HNSW index on `faces.embedding` using `vector_cosine_ops`.
- Use `CREATE INDEX IF NOT EXISTS` so the migration is idempotent.
- Use default HNSW build params (`m=16, ef_construction=64`). Do NOT introduce env-var knobs.
- Inspect the migration runner in `internal/database/postgres/migrations.go`. If it executes each migration inside a transaction, `CREATE INDEX CONCURRENTLY` is not allowed — leave the index build blocking. Add a comment in the migration file noting that the first server start after deploy will block while building the indexes on populated tables (expected: minutes on a 50k-row table on the Pi). If the runner already runs migrations outside a transaction, prefer `CONCURRENTLY`.

### 2. Rewrite similarity-search query layer
- Rewrite the HNSW-backed methods in `internal/database/postgres/embeddings.go` and `internal/database/postgres/faces.go` so they run pure SQL against pgvector using the `<=>` cosine-distance operator. Preserve all method signatures on the existing reader/writer interfaces — only the implementation changes.
- For each query that previously used the in-memory HNSW, do the following inside a single DB transaction (or `SET LOCAL`-compatible session):
  - `SET LOCAL hnsw.ef_search = 100;`
  - `SELECT ... FROM <table> ORDER BY embedding <=> $1 LIMIT $N`
  - Translate any current filters (e.g. min face size for `Match`, exclusion of archived photos, photo-uid exclusion lists) into SQL `WHERE` clauses.
- Hardcode `ef_search = 100` as a package-level constant in `internal/database/postgres/`. Do not expose it as an env var.
- If a query needs filtered results and the SQL `WHERE` clause appears to drop recall too aggressively, oversample (request `3 * limit` candidates, then post-filter in Go and slice). Keep the simpler `WHERE`-only approach as the default; only oversample if integration testing shows fewer-than-expected hits.

## Edge Cases
- Empty `embeddings` or `faces` table at migration time: pgvector allows creating an HNSW index on an empty table. No special handling needed.
- Existing pre-migration `.hnsw` files left in the data dir: do not try to clean them up automatically. Mention in the migration comment that operators can `rm` them once the new code is deployed.
- Operator restoring an old dump taken before this migration: the next `serve` startup will auto-apply migration 035 and build the indexes. That first startup may be slow on large DBs; this is acceptable.
- A handler that previously called `Rebuild()` on the in-memory index after a bulk insert: pgvector maintains the index incrementally, so the call has no replacement — just remove it.
- pgvector dimension cap: 2000 dims; both 512 and 768 are well within it.

## Implementation Notes (read before coding)
- Use parameterized queries — never string-concat a vector into SQL. The pgx driver's `pgvector` integration handles `[]float32` <-> `vector` directly.
- `<=>` returns cosine distance in `[0, 2]`. Where existing code expressed thresholds as "confidence in [0,1]", convert at the boundary (e.g., `distance = 1 - confidence`).
- The `SET LOCAL hnsw.ef_search` must be inside the same transaction as the SELECT; if you use auto-commit single statements, use `SET` instead (but prefer wrapping in a small transaction for clarity).
- When migrating album suggestion centroid search: compute the centroid via `SELECT AVG(embedding) FROM embeddings WHERE photo_uid IN (...)`. Cast/handle as needed; pgvector supports `AVG` on `vector`.
- The face index currently keys on int64 (face row IDs). The pgvector index does not need this — queries naturally join back to the `faces` row via its primary key. No keyspace bridge required.
