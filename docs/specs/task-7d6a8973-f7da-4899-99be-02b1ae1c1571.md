# Audit and refresh README.md

Bring the top-level `README.md` in sync with the current state of the codebase. The README is the project's entry point — it must accurately describe what photo-sorter is, what it does today, and how to run it.

## Scope

- File to edit: `README.md` only.
- Source of truth: actual code under `cmd/`, `internal/`, `web/`, `Dockerfile`, `Makefile`, `docker-compose.yml`, `.goreleaser.yaml`, `deb/`, and the per-feature docs under `docs/`.

## What to verify and update

Walk through every section of the current README and check it against reality:

1. **Project description** — photo-sorter is now a self-contained Go binary + Postgres (pgvector) + external embeddings service. The legacy PhotoPrism dependency is gone (only the migration commands retain a REST client).
2. **Feature list** — must reflect what actually exists in the codebase today, including (but not limited to): native upload pipeline with HEIC/RAW decoding, near-duplicate detection, AI sort/labels/dates, face matching, similarity + text search, photo books with LaTeX PDF export, smart albums (saved searches), public album share links (optional password + expiry), non-destructive photo edits (crop/rotate/brightness/contrast), slideshow + TV presentation mode, soft-delete trash with 30-day auto-purge, EXIF editing with XMP sidecar writes, Czech-aware full-text search, mobile capture page / PWA install, audit log, local user management (admin/editor/viewer), MCP server, migration from PhotoPrism.
3. **Installation / quickstart** — must describe both the Docker path and the `.deb` package released via goreleaser. Verify bootstrap admin env vars (`BOOTSTRAP_ADMIN_USERNAME`, `BOOTSTRAP_ADMIN_PASSWORD`) and database setup steps.
4. **Configuration table** — env vars must match the current `internal/config/` loader (database, storage paths, embeddings, AI providers, web, trash retention, duplicate thresholds, MCP token, etc.). Remove env vars that no longer exist.
5. **CLI examples** — every command shown must actually exist (`serve`, `sort`, `upload`, `albums`, `labels`, `photo`, `cache`, `users`, `backup`, `db-export`, `db-import`, `migrate-from-photoprism`, `migrate-verify`, `migrate-remap-references`, `version`).
6. **Links** — point to the right docs (`docs/architecture.md`, `docs/API.md`, `docs/cli-reference.md`, `docs/web-ui.md`, `docs/photo-book.md`, `docs/markers.md`, `docs/era-estimation.md`, `docs/similarity-search.md`, `docs/migration-from-photoprism.md`, `docs/backup.md`, `docs/testing-environment.md`). Remove broken links.
7. **Screenshots / badges** — if any are referenced, verify the files exist under `screenshots/` and are still representative.

## Rules

- The code is the source of truth. If the README claims a feature that does not exist, remove the claim. If the codebase has a feature the README does not mention, add it.
- Do NOT invent features, env vars, CLI flags, or endpoints. Only document what you can grep for.
- Preserve the existing structure unless a section is genuinely misleading. Prefer surgical edits over a full rewrite.
- Keep the README scannable — feature list bulleted, configuration tabular, examples in fenced code blocks.
- Do not duplicate content that already lives in `docs/`; link to it instead.
- Run `git log --oneline -- README.md` and skim the last 6 months of commits touching anything in `cmd/`, `internal/web/`, `internal/photopipe/`, and `internal/latex/` to find newly added features the README may have missed.

## Done when

- `README.md` accurately reflects the codebase as of the current commit.
- Every claim in the README can be grounded in a specific file, command, env var, or endpoint that exists today.
- Links to `docs/*.md` files all resolve.
- No mention of dropped functionality (e.g. legacy PhotoPrism runtime dependency, MariaDB dev service, removed env vars).
