## What to verify and update

### docs/markers.md

1. Confirm the description of the `markers` table columns matches the current migration.
2. Describe how faces from the embeddings DB (InsightFace) are matched to markers via IoU in display coordinate space (threshold ≥ 0.1).
3. Coordinate handling — both markers and InsightFace embeddings live in display-space; EXIF orientations 5-8 require swapping raw file dimensions for display; document the helper that handles this.
4. Minimum face size — `GetPhotoFaces` does NOT filter; the `Match` endpoint applies the constants (`MinFaceWidthPx`, `MinFaceWidthRel`) from `internal/constants`.
5. Unmatched markers — appended with negative `face_index` (-1, -2, …), `bbox_rel` from marker coordinates, no suggestions.
6. Outlier detection — centroid of a subject's face embeddings; rank by cosine distance; faces with missing embeddings get `face_index: -1`, `dist_from_centroid: -1`.
7. Name normalization — `GetFacesBySubjectName` uses `facematch.NormalizePersonName` (remove diacritics, lowercase, dashes→spaces) backed by the `unaccent` PostgreSQL extension.
8. Apply-face actions — `assign_person`, `unassign_person`, `create_marker`; cross-link to `POST /api/v1/faces/apply`.

### docs/similarity-search.md

1. State clearly that all cosine queries run in pgvector; no app-side in-memory vector arrays.
2. Embedding dimensions — CLIP `embeddings.embedding` is 768-dim; face `faces.embedding` is 512-dim ResNet100.
3. HNSW indexes — both columns have an HNSW index with operator class `vector_cosine_ops` (migration `038_pgvector_hnsw_indexes.sql`).
4. Query pattern — every query opens a small read-only transaction, runs `SET LOCAL hnsw.ef_search = 100`, then `ORDER BY embedding <=> $1::vector`. Document where the constant lives (`internal/database/postgres/embeddings.go`).
5. Maintenance — pgvector keeps indexes up to date on INSERT/UPDATE/DELETE; no manual rebuilds needed.
6. Centroid computation — `GetCentroid` uses `AVG()` over the vector column.
7. Link from `docs/architecture.md`.
